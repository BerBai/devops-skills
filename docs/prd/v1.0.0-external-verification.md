# v1.0.0 外部环境验证矩阵

## 背景

`v1.0.0` 已发布（tag `v1.0.0`，commit `65b0348`），GitHub Actions 的 `test`
（3.8 / 3.10 / 3.12）、`lint`、`floor`、`docs` 全部通过。默认测试套件是
skip-safe 的：没有外部环境时，相关测试会跳过而不是伪造通过。

因此仍有一批能力只能证明到 `logic-tested`，没有到 `backend-verified` 或
`device-verified`。这不是产品失败，但也不能写成“已验证”。本 PRD 把这些
项目变成一份可执行、可验收、可关闭的清单。

`tests/README.md` 对验证级别有定义：

| 级别 | 含义 | 证据 |
|---|---|---|
| `logic-tested` | 离线单测覆盖分支 | `pytest tests/ -m "not live_ssh"` 输出 |
| `backend-verified` | 三条最小命令打到真实后端 | 命令、stdout/stderr、exit code |
| `device-verified` | 真实交换机/防火墙应答 | `ssh_session.py` transcript |

## 目标

- 每一项外部验证都有明确的**环境要求、执行命令、证据格式、验收标准**。
- 每项最终落到 `backend-verified` / `device-verified`，或明确 `deferred`
  并写明原因、负责人和复审日期；不允许长期停留在无说明的 `unverified`。
- 默认 CI 仍不依赖外部环境；验证结果通过 issue/PR 证据和
  `CLAIM-LEDGER.md` 更新来记录，而不是把 live 测试塞进每次 push。

## 非目标

- 不为通过验证而修改产品行为；验证中发现的缺陷另开 issue。
- 不连接生产主机、不写入生产集群、不使用真实客户凭据。
- 不把 live 测试变成默认 CI 的必跑项。
- 不因为验证补跑而移动 `v1.0.0` tag；验证属于 post-release 工作。

## 环境矩阵

| ID | 验证项 | 需要的外部环境 | 最低验证入口 | 当前状态 | 优先级 |
|---|---|---|---|---|---|
| E1 | 真实 SSH 主机（pai） | `192.168.2.0/24` 可达的 `pai` / 任意测试 alias | `POC_HOST=pai pytest -m live_ssh` + 三条最小命令 | 未验证：CI 未设 `POC_HOST` | P0 |
| E2 | Docker / Podman | 运行中的 Docker daemon + 一个测试容器/镜像/compose 项目 | `inspect_container` / `image_audit` / `compose_status` | 未验证：无默认 `live_docker` 套件 | P0 |
| E3 | Kubernetes | kind + kubectl + helm + Docker | `pytest -m live_k8s` 或三条最小命令 | 未验证：默认 skip | P1 |
| E4 | Terraform / OpenTofu | `terraform` 或 `tofu` + `python-hcl2` + 已 init 的 fixture | `pytest -m live_terraform` + 三条最小命令 | 未验证：本机未安装 | P1 |
| E5 | GitHub / GitLab CI | `gh` 登录 + 测试仓库；或 `glab` 登录 | `pytest -m "cicd_gh or cicd_glab"` | 未验证：无测试仓库/凭据 | P1 |
| E6 | Windows 目标 | 原生 Windows + PowerShell/cmd | `ssh_execute.py` / `ssh_upload.py` / `--shell` 的 Windows 路径 | 未验证：无 Windows 主机 | P2 |
| E7 | password-only SSH | 只允许密码登录的测试主机 + `SSH_PASSWORD` | exec / upload / tunnel 三条命令 | 未验证：无 password-only 主机 | P1 |
| E8 | 离线安装 | 联网构建机 + 无外网 Linux 目标 | `build_offline_bundle.sh` → `install_offline_linux.sh` → `selfcheck`/`doctor` | 未验证：未构建离线包 | P0 |
| E9 | 外部 URL | 可访问外网 | `check_docs_links.py --external` | 未验证：门禁默认不抓外网 | P2 |
| E10 | UDP 防火墙语义 | 可控的丢弃/拒绝 UDP 的测试网络 | `port_check.py --udp` | 未验证：未复现 `open-or-filtered` | P2 |
| E11 | daemon 加速比 | 同一主机、可控 RTT | 5 次 fresh vs daemon 调用 | 未验证：只有单次 0.292s 样本 | P2 |

## 需求

### E1（P0）真实 SSH 主机

- 环境：能 `ssh pai` 的机器，且本机在 `192.168.2.0/24`（CLAUDE.md 约束）。
- 执行：
  ```bash
  POC_HOST=pai pytest tests/ -m live_ssh -v
  ssh_execute.py pai "uname -srm" --json
  ssh_upload.py pai ./probe.txt /tmp/probe.txt --overwrite --json
  ssh_download.py pai /tmp/probe.txt ./probe.copy.txt --json
  ```
- 证据：完整 pytest 结果 + 三条命令的 JSON envelope + exit code；上传/下载
  用 `cmp` 证明字节一致；清理 `/tmp/probe.*`。
- 验收：`live_ssh` 0 failed（允许因环境明确 skip 的用例逐条列出），三条
  命令 exit 0 且 envelope `success: true`；`pai` 主机名/Debian 版本记录在
  transcript。
- 风险：测试可能写入 `pai` 的 `/tmp`/`~/.devops`；先确认 disposable，测试
  后清理。
- 观察（2026-11-11）：本机 `en0` 为 `192.168.79.147`，不在 `192.168.2.0/24`，
  `ssh pai` 返回 `Connection closed by 192.168.2.115 port 22`。因此按 CLAUDE.md
  的约束跳过验证阶段；E1 必须在实验室网段内执行。

### E2（P0）Docker / Podman

- 环境：`docker info` 成功；准备一个测试容器、一个测试镜像、一个 compose
  项目（可用 `tests/fixtures/backends/compose.docker.yml`）。
- 执行：
  ```bash
  docker info
  inspect_container.py local <name|id> --json
  image_audit.py local <image> --json
  compose_status.py local <project-dir> --json
  ```
- 证据：三条 JSON envelope + exit code；容器/镜像/compose 的创建命令和清理
  命令；`--runtime podman` 如可用则补一条。
- 验收：三条命令 exit 0；`data.findings` 与容器实际状态一致；无写入操作。
- 风险：`docker` 在 CI runner 存在不代表 daemon 可用；必须显式 `docker info`。

### E3（P1）Kubernetes

- 环境：`kind`、`kubectl`、`helm`、运行中的 Docker；kind 集群名
  `k8s-debug-test`（见 `tests/conftest.py`）。
- 执行：
  ```bash
  pytest tests/test_check_namespace_integration.py tests/test_diagnose_pod_integration.py \
         tests/test_cluster_health_integration.py tests/test_helm_status_integration.py \
         -m live_k8s -v
  ```
  或 `pytest -m live_k8s`。
- 证据：pytest 结果 + `kind get clusters` + 三条最小命令的 envelope；测试后
  `kind delete cluster --name k8s-debug-test`（或明确说明复用）。
- 验收：`live_k8s` 0 failed；`check_namespace` / `diagnose_pod` /
  `helm_status` 至少各一条真实输出；没有对非测试集群执行写操作。
- 风险：kind 创建可能超时；CI 默认不跑，验证环境需显式清理。

### E4（P1）Terraform / OpenTofu

- 环境：`terraform` 或 `tofu`、`python-hcl2`；`tests/fixtures/backends/` 中
  已 init 的项目（见 `tests/fixtures/backends/README.md`）。
- 执行：
  ```bash
  pytest -m live_terraform -v
  state_inspect.py local <project-dir> --json
  drift_check.py local <project-dir> --json
  module_validate.py local <module-dir> --json
  ```
- 证据：三条 envelope + `terraform version`/`tofu version` + fixture 的
  `terraform init` 记录；`plan -detailed-exitcode` 的 0/2 结果。
- 验收：`live_terraform` / `live_iac` 0 failed（依赖缺失的 skip 逐条列出）；
  `drift_check` 对已知 drift fixture 返回预期分类；无 `apply/destroy`。
- 风险：fixture 可能需要真实云凭据；优先用 `terraform_data`/local provider，
  避免云费用。

### E5（P1）GitHub / GitLab CI

- 环境：`gh auth status` 成功 + `CICD_GH_REPO` 指向测试仓库；或 `glab` 登录。
- 执行：
  ```bash
  pytest -m "cicd_gh or cicd_glab" -v
  pipeline_analyzer.py gh <run-id> --project <owner/repo> --json
  runner_check.py gh --repo <owner/name> --json
  secret_scope_audit.py gh --repo <owner/name> --json
  ```
- 证据：pytest 结果 + 三条 envelope；`gh auth status` / `glab auth status`
  的脱敏输出；测试仓库名可公开或脱敏。
- 验收：`cicd_gh` / `cicd_glab` 在凭据存在时 0 failed；缺少凭据时明确 skip，
  不得把 skip 写成 pass；不触发 rerun/cancel/写 workflow。
- 风险：token scope 过大；使用只读测试仓库，验证后 revoke。

### E6（P2）Windows 目标

- 环境：原生 Windows（PowerShell 5.1 或 pwsh）+ OpenSSH 客户端。
- 执行：`ssh_execute.py`（`--shell cmd|powershell`、Windows 路径）、
  `ssh_upload.py`（MSYS 路径转换）、`doctor.py`（askpass ACL）。
- 证据：三条 `--json` envelope + `data.shell` / `data.transport`；Windows
  版本、PowerShell 版本；不包含密码。
- 验收：Windows 路径不被 MSYS 改写；`cmd /c` / `powershell -Command` 被识别；
  askpass 目录 ACL 收紧且登录成功。
- 风险：没有 Windows 主机时只能保持 `unverified`，不能以 POSIX 结果代替。

### E7（P1）password-only SSH

- 环境：只允许密码/keyboard-interactive 的测试主机；`SSH_PASSWORD` 环境变量。
- 执行：
  ```bash
  SSH_PASSWORD=... ssh_execute.py <host> "uptime" --auth password --json
  SSH_PASSWORD=... ssh_upload.py <host> ./probe.txt /tmp/probe.txt --overwrite --json
  SSH_PASSWORD=... ssh_tunnel.py start <host> --remote-port 80 --local-port 18080 --auth password --json
  ```
- 证据：三条 envelope；确认 `ssh_argv`、`stdout`、`stderr`、audit log 中没有
  密码；`ps`/`/proc` 检查（可选）；tunnel 停止并清理。
- 验收：三条命令 exit 0；缺 `SSH_PASSWORD` 时 `password_required`（105）；
  bare IP 无 user 时 `user_required`（115）；密码不出现在证据里。
- 风险：密码泄露；只在 disposable 主机上验证，证据必须脱敏。

### E8（P0）离线安装

- 环境：联网构建机（可跑 `uv`/下载 wheels）+ 无外网 Linux 目标。
- 执行：
  ```bash
  scripts/build_offline_bundle.sh --output-dir dist/
  tar xf dist/devops-skills-*-linux-offline-*.tar.gz
  ./install_offline_linux.sh --prefix "$HOME/.local/share/devops-skills"
  "$PREFIX/repo/plugins/ssh-core/skills/ssh-core/scripts/run.sh" selfcheck.py
  "$PREFIX/repo/plugins/ssh-core/skills/ssh-core/scripts/run.sh" doctor.py
  ```
- 证据：bundle 名称/大小/内容清单、目标机 `uname -a`、安装日志、
  `selfcheck`/`doctor` 输出；目标机断网证明。
- 验收：安装后 `selfcheck` 必需项全通过；`doctor` 无回归；插件树能定位
  ssh-core；目标机不访问外网。
- 风险：wheels 平台/ABI 不匹配；目标机 Python 3.8 floor。

### E9（P2）外部 URL

- 环境：稳定外网。
- 执行：
  ```bash
  python scripts/check_docs_links.py --external
  ```
- 证据：命令输出 + 失败 URL 列表（若有）；记录网络出口/时间。
- 验收：8 个外部 URL 全部 2xx/3xx；失败项单独记录，不阻断默认 docs job。
- 风险：外网不稳定；不得把偶发超时写成断链。

### E10（P2）UDP 防火墙语义

- 环境：可控的测试网络，能制造 ICMP port-unreachable 和静默丢包两类结果。
- 执行：
  ```bash
  port_check.py <source> --target <target> --ports 53 --udp --json
  ```
- 证据：两次结果（`refused` 与 `open-or-filtered`）+ 防火墙规则/抓包。
- 验收：两种结果都被正确分类；`source-error` 只在源端无探测能力时出现。
- 风险：需要网络设备配置权限；不得在客户网络做。

### E11（P2）daemon 加速比

- 环境：同一主机、可控 RTT、干净网络。
- 执行：5 次 `ssh_execute.py` fresh 调用 vs 5 次 `ssh_daemon.py` 调用；
  记录 wall time。
- 证据：原始计时表 + 中位数/均值；不要只引用单次 0.292s。
- 验收：给出可复现的加速比，或在 README/SKILL 中删除/限定 “≈3x” 措辞。
- 风险：结果依赖 RTT；必须记录网络条件，不能外推。

## 证据规范

每条验证记录至少包含：

1. `command`（完整 argv，不含密码）；
2. `stdout` / `stderr` / `exit code`；
3. 环境：OS、Python、工具版本、目标主机/集群、日期、操作者；
4. 关联的 commit/tag（当前应为 `v1.0.0` / `65b0348` 或后续 post-release commit）；
5. 清理动作与结果（容器/集群/临时文件/凭据）。

证据放在 tracking issue 或 PR 描述中；如写入仓库，放在 PR 评论或独立的
`docs/verification/`（本 PRD 不预创建该目录）。完成后同步：

- 将 `CLAIM-LEDGER.md` §F 的对应行改为 `verified`，或改为 `deferred` 并写
  明原因/负责人/日期；
- 不在 `SECURITY.md` / README 中把未验证项写成已保证的能力。

## 验收标准

- E1–E11 每项都有 `verified` 或 `deferred` 状态，没有无说明的 `unverified`。
- 至少 P0（E1/E2/E8）完成并附证据；P1 有明确计划。
- 所有命令有 transcript 和 exit code；失败项有复现 issue。
- 默认 CI 仍全绿；没有把 live 测试变成 push 必跑项。
- 证据中无密码、私钥、token、客户主机名。
- `v1.0.0` tag 不因验证补跑移动；验证提交不带 tag。

## 约束

- `pai` 只在 `192.168.2.0/24` 可达时使用（CLAUDE.md）。
- 所有测试主机/集群/容器必须 disposable；验证后清理。
- 凭据只通过环境变量或已登录 CLI 注入，不写文件、不进 argv、不进证据。
- 保持 Python 3.8 floor；不因验证引入新运行时依赖。
- 不修改产品行为来“让验证通过”；发现缺陷另开 issue。

## 风险

- 环境漂移：今天 pass 不代表下月 pass；证据要带版本和日期。
- 外部服务不稳定：E5/E9 可能因网络/配额失败，不能直接判产品失败。
- 凭据泄露：E5/E7 是高风险项，证据必须脱敏。
- 成本：E3/E4 可能创建云资源；优先 local/kind/fixture。
- 误判：skip 不是 pass；`live_k8s` / `live_terraform` 默认 skip 必须在报告里
  写成 skipped，而不是 verified。
